# 16. Ring 3、系统调用与内核入口

## 本章定位

此前我们已经讨论了用户态/内核态、Ring 3 应用执行 `syscall` 后进入 Ring 0，以及为什么这不代表应用获得内核全部权限。本章把这些概念连成一条硬件与内核协作链路。这里是原理整理和后续实现的准备，不表示 RustOS 已经具备可运行的 Ring 3 用户程序。

## 用户程序可以执行 syscall 指令吗？

可以。系统调用指令本来就是提供给用户态程序使用的受控入口。应用执行 `syscall` 后，CPU 根据预先配置的系统调用入口寄存器切换到内核特权级，并从内核入口地址继续执行。

这不是把应用代码永久升级为 Ring 0。CPU 只转移控制流到内核预先指定的入口；内核负责检查系统调用号、参数、用户指针、权限和资源状态。内核处理完成后，再通过受控返回指令回到用户态。

## x86_64 SYSCALL 大致做了什么

在长模式下，`SYSCALL` 的关键行为由 MSR 配置控制，概念上包括：

1. 根据 `IA32_LSTAR` 等配置取得内核入口地址。
2. 根据 `IA32_STAR` 中的选择子配置建立内核代码段/栈段相关的段状态。
3. 将用户返回 RIP 保存到 `RCX`。
4. 将用户 `RFLAGS` 保存到 `R11`，并按 `IA32_FMASK` 屏蔽指定标志。
5. 进入 Ring 0 并从内核入口开始执行。

重要限制：`SYSCALL` 不会自动保存所有通用寄存器，也不会自动把 RSP 切换到内核栈。内核入口汇编必须按照自己的 ABI 保存必要状态，并从安全的 per-CPU 数据中取得当前线程的内核栈。不能假设用户 RSP 可以直接作为内核栈使用。

## 内核栈如何选取

内核为每个线程准备独立内核栈。系统调用入口通常需要通过每 CPU 数据、`swapgs` 约定或其他架构相关机制找到当前线程的内核栈，再切换 RSP。具体实现必须遵守 CPU 手册、GDT/MSR 配置和内核入口汇编约定。

不要把 `SYSCALL` 与通过 IDT 进入的中断/异常路径混为一谈。中断/异常在特定配置下可以通过 TSS 中的 RSP0/IST 取得栈；`SYSCALL` 的栈切换机制需要内核入口代码自己设计。

## 系统调用与线程调度不是同一件事

系统调用通常是当前线程从用户态进入内核态继续执行。它可能很快返回同一线程，也可能因为等待 I/O、锁或其他事件而阻塞；只有当调度器决定运行其他线程时，才发生线程上下文切换。

所以：

- **特权级切换**：Ring 3 与 Ring 0 之间的控制权切换。
- **上下文切换**：CPU 从一个线程的执行状态切换到另一个线程。
- **地址空间切换**：必要时更新当前逻辑 CPU 的 CR3，使其使用另一个进程的页表根。

它们可能在一次系统调用过程中连续发生，但不是同一个概念。

## 内核必须验证用户指针

用户程序传给系统调用的指针属于用户虚拟地址空间。内核不能因为一个整数“看起来像地址”就直接解引用。内核需要确认地址范围合法、映射存在、权限允许、长度计算没有溢出，并处理并发撤销映射等风险。某些内核会通过安全的 copy-in/copy-out 辅助函数在用户空间和内核缓冲区之间复制数据。

## 后续实现顺序

RustOS 后续实现 Ring 3 和系统调用时，建议按以下顺序推进：

1. 建立 GDT、TSS 和 IDT 的最小正确配置。
2. 为每个线程准备用户栈与内核栈。
3. 配置 `SYSCALL` 所需 MSR 和 per-CPU 内核入口状态。
4. 编写入口汇编，保存/恢复寄存器并切换栈。
5. 实现最小系统调用分发器，例如 `write` 或 `exit`。
6. 从用户态运行一个最小程序，验证受控进入与返回。

## 思考题

1. 用户程序执行 `syscall` 后，为什么没有获得 Ring 0 的永久权限？
2. `SYSCALL` 会自动保存所有通用寄存器吗？会自动切换 RSP 吗？
3. 系统调用进入内核态是否必然导致线程切换？
4. 为什么内核不能直接信任用户程序传入的指针？

## 本课结论

系统调用是 CPU 提供的受控特权级入口与内核软件协议的组合。硬件负责按配置改变特权级和控制流，内核负责保存上下文、切换安全栈、验证参数、执行服务并安全返回。


## 代码演示：系统调用分发器的 Rust 侧形状

**来源标记：新增补充示例。** 下面只展示内核拿到系统调用号和参数后的分发层，不包含尚未实现的汇编入口、MSR 初始化、用户栈切换和返回路径。

```rust
#[derive(Debug, Clone, Copy)]
pub enum SyscallError {
    UnknownSyscall,
    InvalidUserPointer,
    PermissionDenied,
}

const SYS_EXIT: u64 = 0;
const SYS_WRITE: u64 = 1;

pub fn dispatch_syscall(
    number: u64,
    args: [u64; 6],
) -> Result<u64, SyscallError> {
    match number {
        SYS_EXIT => {
            let exit_code = args[0];
            sys_exit(exit_code)
        }
        SYS_WRITE => {
            let user_pointer = args[0];
            let length = args[1];
            sys_write(user_pointer, length)
        }
        _ => Err(SyscallError::UnknownSyscall),
    }
}

fn sys_exit(_code: u64) -> Result<u64, SyscallError> {
    // 后续由线程管理器把当前线程标记为退出。
    // 当前课程尚未实现完整线程生命周期。
    Ok(0)
}

fn sys_write(
    _user_pointer: u64,
    _length: u64,
) -> Result<u64, SyscallError> {
    // 不能直接把用户传入的整数当作内核指针解引用。
    // 后续需要验证用户地址范围并执行 copy_from_user。
    Err(SyscallError::InvalidUserPointer)
}
```

### 为什么 sys_write 不能直接解引用参数

用户传入的指针属于当前进程的用户虚拟地址空间。内核必须验证地址范围、长度加法是否溢出、页是否映射、权限是否允许，并防止并发撤销映射。正确的实现通常先把用户数据安全复制到内核缓冲区，再交给设备或文件系统处理。

### 硬件入口与 Rust 分发层的边界

```text
Ring 3 执行 syscall
    |
CPU 根据 IA32_LSTAR 等配置进入 Ring 0
    |
汇编入口保存寄存器、切换到线程内核栈
    |
构造 syscall frame
    |
dispatch_syscall(number, args)
    |
执行服务并准备返回值
    |
汇编恢复用户上下文并返回 Ring 3
```

`SYSCALL` 会把用户返回 RIP 保存到 RCX，把用户 RFLAGS 保存到 R11；它不会自动保存所有通用寄存器，也不会自动把 RSP 切换到内核栈。当前 RustOS 还没有实现这条完整路径，所以本节分发器是接口设计示例，不是可从 Ring 3 调用的现成功能。
