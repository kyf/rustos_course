# 01. 操作系统究竟做什么

## 本课目标

理解操作系统的核心职责，回答：没有 OS 能否运行程序？为什么需要用户态和内核态？系统调用与普通 OS API 有什么关系？

## 没有 OS，程序能运行吗？

可以。CPU 上电后会从架构规定的启动入口开始执行固件代码；启动链路可以最终加载一个裸机程序。这个程序可以直接读写设备寄存器、处理中断和使用内存。

问题在于，如果所有程序都直接控制硬件，就需要每个程序自己处理设备初始化、内存使用、中断和资源冲突。多个程序之间也没有天然的隔离与调度机制。

操作系统主要负责：

- **资源管理**：分配 CPU 时间、内存和设备。
- **隔离与保护**：避免一个程序任意破坏另一个程序或内核。
- **抽象**：把复杂硬件包装成进程、文件、网络套接字等接口。
- **并发与调度**：决定何时运行哪个任务。
- **统一服务入口**：让应用通过受控接口请求内核能力。

## 用户态与内核态

x86 常见特权级概念包括 Ring 0 和 Ring 3：

- Ring 0：内核态，允许执行特权指令并访问受保护资源。
- Ring 3：用户态，权限受限，不能任意执行特权操作。

如果所有代码都运行在 Ring 0，一个普通应用的 bug 就可能破坏整个系统。权限隔离让应用只能通过内核提供的受控入口申请资源。

## 系统调用与 OS API

- **系统调用**：用户程序从用户态进入内核态、请求内核服务的受控机制。
- **OS API**：操作系统向程序提供的接口集合，可能由语言库、运行时或系统库提供。

应用调用文件读取函数时，库函数可能先处理缓冲、参数和错误格式，再通过系统调用进入内核。因此一个 OS API 不一定与一个系统调用一一对应。

## 执行 syscall 后，应用程序会获得 Ring 0 权限吗？

不会。系统调用是一条受控的特权级转换路径。用户程序执行 `syscall` 后，CPU 按预先配置的系统调用入口状态转到内核态执行内核入口代码；它并没有把用户程序剩余代码整体升级成 Ring 0。内核检查系统调用号、参数、用户指针和权限，只执行允许的操作，随后通过受控返回路径回到用户态。

在 x86_64 中，`SYSCALL` 指令会根据配置的 Model-Specific Registers 设置内核代码段/入口地址，并保存用户返回地址和标志位到指定寄存器；它不会自动保存所有通用寄存器，也不会自动为内核选择一个安全的 RSP。内核入口汇编必须按约定保存状态，并切换到当前线程的内核栈。具体入口细节将在后续系统调用课程中实现。

系统调用进入内核态也不等于发生了进程切换。它通常仍在同一线程上下文中执行内核服务，内核可能在之后因为阻塞或调度决定而切换到其他线程。

## 为什么需要调度

多个任务共享 CPU 时，OS 需要决定哪个任务先运行、一个任务运行多久、任务等待 I/O 时是否切换到其他任务，以及如何恢复被中断任务的执行状态。调度器负责策略；上下文切换负责保存和恢复执行状态。

2. 用户程序调用 `read()` 时，为什么不能直接访问磁盘控制器？
3. 系统调用和 C 标准库函数为什么不一定一一对应？
4. 如果所有任务都在内核态运行，系统会失去哪些保护能力？

## 本课结论

OS 不是 CPU 执行程序的唯一条件。它的核心价值在于管理硬件资源、隔离、调度，并向程序提供稳定抽象和受控服务。


## 代码演示：一个普通 OS API 调用背后发生了什么

**来源标记：新增补充示例。** 这是运行在宿主操作系统上的普通 Rust 程序，不是 RustOS 内核代码。它用来区分“应用调用的 API”和“CPU 进入内核的系统调用机制”。

~~~rust
use std::{fs, io};

fn main() -> io::Result<()> {
    // 应用调用的是 Rust 标准库提供的文件 API。
    let text = fs::read_to_string("/etc/hosts")?;

    println!("read {} bytes", text.len());
    Ok(())
}
~~~

### 这段代码为什么不是一次直接的硬件访问

应用只表达了“读取一个文件”的意图。它没有初始化磁盘控制器，也没有直接向磁盘设备寄存器发送命令。标准库会通过当前平台的系统接口请求操作系统完成文件读取。

概念调用链如下：

~~~text
Rust 应用
  |
std::fs::read_to_string
  |
平台运行库 / OS 适配层
  |
系统调用入口（例如 read/open 一类服务）
  |
内核检查参数、权限与文件描述符
  |
文件系统 / 缓存 / 块设备驱动
  |
返回数据或错误
~~~

这条链路是概念示意，不表示所有平台都采用完全相同的函数名或内部实现。macOS、Linux 和 Windows 的系统调用 ABI 不同；Rust 标准库的公开 API 可以相对稳定，但底层调用路径由目标操作系统决定。

### API 和 syscall 为什么不是一回事

- 应用调用的 API 是一层软件接口，可能负责缓冲、编码、参数转换和错误封装。
- syscall 是 CPU 和内核约定的受控入口，负责从用户态转入内核态。
- 一个 API 可能触发多个系统调用；某些 API 也可能完全在用户态完成，不需要进入内核。

后续第 16 章会把系统调用分发器的 Rust 侧形状具体化。这里先记住：**应用调用的是抽象接口，内核提供的是受控服务，硬件提供的是特权级转换机制。**
