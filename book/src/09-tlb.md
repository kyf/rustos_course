# 09. TLB：页表修改后为什么还不够

## TLB 是什么

TLB（Translation Lookaside Buffer）是 CPU 用来缓存近期地址转换结果的硬件结构。页表可能需要多次内存访问才能完成一次地址转换；TLB 可以缓存 VA → PA 的转换和相关权限信息，减少重复遍历页表的成本。

```text
CPU 访问 VA
   |
查询 TLB
   | 命中 -> 使用缓存的 PA / 权限
   | 未命中
   v
遍历页表 -> 得到转换 -> 更新 TLB
```

## 为什么改了页表还要刷新

假设虚拟地址 `0x4000_0000` 原来映射到 Frame A，CPU 已经把这个转换缓存到 TLB。内核随后把 PTE 修改为 Frame B。如果 TLB 仍保留旧转换，CPU 可能继续访问 Frame A。

因此修改映射后，必须让相关 CPU 不再使用过期转换。

## 常见刷新方式

- **INVLPG**：使指定线性地址对应的 TLB 项失效。
- **重新加载 CR3**：在传统未启用 PCID 的场景下，通常会刷新当前地址空间相关的非全局 TLB 项。
- **PCID**：启用后，TLB 项可以按地址空间标识保留，刷新语义更细。
- **Global Page**：某些全局映射可能不因普通 CR3 切换而失效，需要按架构规则处理。

因此，不要把“写 CR3 一定清空所有 TLB”当成所有配置下的绝对规则。

## MapperFlush

`x86_64` crate 的映射 API 常见设计是：修改页表后返回一个 flush 对象，由调用者显式调用 `flush()` 或等价方法。

```rust
let flush = mapper.map_to(page, frame, flags, allocator)?;
flush.flush();
```

这段代码只表达“修改映射后刷新”的顺序，实际方法签名和错误处理应以项目当前依赖版本为准。

## 多核系统中的额外问题

在单核环境中，使当前 CPU 的 TLB 项失效通常就足够验证基础机制。多核环境更复杂：同一地址空间可能曾在多个 CPU 核心上运行。修改页表后，其他核心的 TLB 也可能缓存旧映射。OS 需要通过跨核中断等机制执行 TLB Shootdown，通知其他核心失效对应缓存。

## 本课结论

页表是内存中的映射数据结构，TLB 是 CPU 内部的转换缓存。正确的内存管理必须同时维护二者的一致性。


## TLB Miss 不等于 Page Fault

TLB Miss 只表示 CPU 的地址转换缓存里没有找到当前地址对应的缓存项。它通常会触发硬件页表遍历：

- 如果页表项存在、权限满足要求，CPU 完成转换并把结果填入 TLB，程序继续执行。
- 如果页表项不存在，或访问违反页表权限，硬件才会产生 Page Fault（#PF）。

因此，TLB Miss 是一次缓存未命中；Page Fault 是硬件报告地址映射不存在或访问权限不满足等情况的异常。二者不能混为一谈。
